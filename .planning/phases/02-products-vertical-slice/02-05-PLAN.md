**2. `frontend/src/features/products/api.ts`** — typed Axios calls:

```ts
import { apiClient } from '@/shared/api/client'
import type { PagedResult } from '@/shared/types'
import type { CreateProductRequest, ProductResponse } from './types'

/**
 * Product API surface. All methods unwrap `response.data` at the boundary so callers
 * receive the typed payload directly. Errors are normalized by the Axios interceptor
 * to `ApiError` (rejected) — callers handle in try/catch.
 */
export const productsApi = {
  list: (page = 1, pageSize = 30, includeDeleted = false): Promise<PagedResult<ProductResponse>> =>
    apiClient
      .get<PagedResult<ProductResponse>>('/products', { params: { page, pageSize, includeDeleted } })
      .then((r) => r.data),

  getById: (id: string): Promise<ProductResponse> =>
    apiClient.get<ProductResponse>(`/products/${id}`).then((r) => r.data),

  create: (req: CreateProductRequest): Promise<ProductResponse> =>
    apiClient.post<ProductResponse>('/products', req).then((r) => r.data),

  delete: (id: string): Promise<void> =>
    apiClient.delete<void>(`/products/${id}`).then(() => undefined),
}
```

The base URL `/api` lives in the Axios singleton (`@/shared/api/client.ts` from Phase 1). Calls written as `/products` resolve to `/api/products` via Vite proxy.

**3. `frontend/src/features/products/schemas/createProductSchema.ts`** — Zod schema. Messages byte-for-byte from UI-SPEC table:

```ts
import { z } from 'zod'

/**
 * Zod schema for `POST /api/products` payload. Messages mirror
 * backend `CreateProductRequestValidator` (Plan 02-01) byte-for-byte per CONTEXT.md D-11.
 *
 * Messages-only-on-frontend (where the backend trusts JSON shape):
 *   - "Tipo é obrigatório", "Valor do fornecedor é obrigatório", "Quantidade inicial é obrigatória"
 *     (Zod sees `null` before user picks a value; FluentValidation never sees the null because
 *     the backend wouldn't be reached without a value coerced).
 *   - "Quantidade inicial deve ser um número inteiro" (Zod's integer check; the JSON `number`
 *     would round-trip fine to the backend's `int` deserialization but Zod surfaces the issue
 *     earlier with a more specific message).
 */
export const createProductSchema = z.object({
  code: z
    .string({ required_error: 'Código é obrigatório' })
    .min(1, 'Código é obrigatório')
    .max(50, 'Código deve ter no máximo 50 caracteres'),

  description: z
    .string({ required_error: 'Descrição é obrigatória' })
    .min(1, 'Descrição é obrigatória')
    .max(200, 'Descrição deve ter no máximo 200 caracteres'),

  type: z.enum(['Electronic', 'Appliance', 'Furniture'], {
    required_error: 'Tipo é obrigatório',
    invalid_type_error: 'Tipo é obrigatório',
    errorMap: () => ({ message: 'Tipo inválido. Valores aceitos: Eletrônico, Eletrodoméstico, Móvel' }),
  }),

  supplierValue: z
    .number({ required_error: 'Valor do fornecedor é obrigatório', invalid_type_error: 'Valor do fornecedor é obrigatório' })
    .nonnegative('Valor do fornecedor não pode ser negativo'),

  initialStockQuantity: z
    .number({ required_error: 'Quantidade inicial é obrigatória', invalid_type_error: 'Quantidade inicial é obrigatória' })
    .int('Quantidade inicial deve ser um número inteiro')
    .nonnegative('Quantidade inicial não pode ser negativa'),
})

export type CreateProductForm = z.infer<typeof createProductSchema>
```

**Why the enum `errorMap`** instead of just `invalid_type_error`: Zod's enum validator emits `invalid_enum_value` for out-of-range strings (different from `invalid_type` for non-strings). The errorMap is the unified hook to control the message regardless of which sub-validator triggered.

**Why `min(1, '...')` AFTER `string({ required_error })`:** `required_error` fires when the field is absent or `undefined`; `min(1)` fires when the field is `""`. Both must produce the same `Código é obrigatório` message (the user experience doesn't care about the technical distinction).

**1. `frontend/src/features/products/composables/useProducts.ts`** — composable wiring API + state:

```ts
import { ref } from 'vue'
import { productsApi } from '../api'
import type { ProductResponse, CreateProductRequest } from '../types'
import type { ApiError } from '@/shared/api/client'
import type { PaginationMeta } from '@/shared/types'

export function useProducts() {
  const items = ref<ProductResponse[]>([])
  const pagination = ref<PaginationMeta>({
    page: 1, pageSize: 30, total: 0, totalPages: 0, hasNext: false, hasPrev: false,
  })
  const loading = ref(false)
  const error = ref<ApiError | null>(null)
  const showDeleted = ref(false)

  /** Fetch a page; rebinds pagination + items; sets error on failure. */
  async function fetchPage(page = pagination.value.page, pageSize = pagination.value.pageSize): Promise<void> {
    loading.value = true
    error.value = null
    try {
      const result = await productsApi.list(page, pageSize, showDeleted.value)
      items.value = result.items
      pagination.value = result.pagination
    } catch (e) {
      error.value = e as ApiError
    } finally {
      loading.value = false
    }
  }

  /** Toggle the "Mostrar excluídos" filter; refetches page 1. */
  async function setShowDeleted(next: boolean): Promise<void> {
    showDeleted.value = next
    await fetchPage(1)
  }

  /** Create a product; refetch page 1 on success (created_at DESC sort lands new entry on top). */
  async function create(request: CreateProductRequest): Promise<ProductResponse> {
    const created = await productsApi.create(request)
    await fetchPage(1)
    return created
  }

  /** Soft-delete and refetch current page (or fall back to a lower page if current became empty). */
  async function softDelete(id: string): Promise<void> {
    await productsApi.delete(id)
    const remainingOnPage = items.value.length - 1
    const nextPage = remainingOnPage === 0 && pagination.value.page > 1
      ? pagination.value.page - 1
      : pagination.value.page
    await fetchPage(nextPage)
  }

  /** Retry after a failed fetch — re-runs fetchPage with last requested page. */
  function retry(): Promise<void> {
    return fetchPage(pagination.value.page)
  }

  return {
    items, pagination, loading, error, showDeleted,
    fetchPage, setShowDeleted, create, softDelete, retry,
  }
}
```

Throws from `create` and `softDelete` bubble up to the caller (the page component decides what toast to show). `fetchPage` catches because failures need to set `error.value` so the page renders the 4th state.

**Currency input contract (comma-decimal, BR locale):** UI-SPEC §"Currency input" line 179 + §"Create Product drawer" line 387 lock the input to `type="text" inputmode="decimal"` with a comma-decimal mask — BR-locale users type `1234,56`, NOT `1234.56`. The `BaseInput` `currency-brl` mask renders the `R$` prefix decoration. The form keeps a raw string `supplierValueRaw` reflecting the user's typing (digits + comma + thousand-dots), and a synced numeric `supplierValue` that is the Zod-validated submit value.

Add inside `<script setup>` (alongside the other `defineField` calls):

```ts
import { computed } from 'vue'

// Raw BR-locale string (what the user types: '1234,56' or '1.234,56'). Mask allows digits, a single comma, and optional thousand-dots.
const supplierValueRaw = ref<string>('')

// Convert raw BR string → number for the form's submit-time value.
function parseBrCurrency(s: string): number {
  if (!s) return NaN
  // Strip thousand-dots, replace decimal comma with dot, then parseFloat.
  return parseFloat(s.replace(/\./g, '').replace(',', '.'))
}

// Mask: while typing, allow only digits + at most one comma. Reject invalid keystrokes.
function onSupplierValueInput(ev: Event): void {
  const target = ev.target as HTMLInputElement
  // Allow digits, a single comma, and a thousand-dot grouping (purely cosmetic mid-typing).
  const cleaned = target.value.replace(/[^0-9.,]/g, '')
  // Enforce at most one comma
  const parts = cleaned.split(',')
  const masked = parts.length > 1 ? parts[0] + ',' + parts.slice(1).join('').replace(/,/g, '') : cleaned
  supplierValueRaw.value = masked
  // Sync numeric form field
  supplierValue.value = parseBrCurrency(masked)
}

// On blur, preview-format to 'R$ X.XXX,XX' so the user sees the locale-correct rendering.
function onSupplierValueBlur(): void {
  const n = parseBrCurrency(supplierValueRaw.value)
  if (!Number.isNaN(n)) {
    // Render as BR-locale decimal with thousands separator and 2 decimal places (no prefix; the mask layer renders R$).
    supplierValueRaw.value = new Intl.NumberFormat('pt-BR', { minimumFractionDigits: 2, maximumFractionDigits: 2 }).format(n)
    supplierValue.value = n
  }
}
```

**Submit-time transform:** the form's `supplierValue` field is already a `number` (parsed from the BR string via `parseBrCurrency`). The Zod schema validates `supplierValue` as a number (non-negative), so the Zod refinement layer is already correct — the BR string lives ONLY in the input element's bound `supplierValueRaw`, never reaches the POST payload.

**Zod schema (Plan 02-05 Task 1) update — required to accept BR-string input on the field if we want Zod to own the parse:** the simplest split is to keep the schema's `supplierValue: z.number().nonnegative(...)` and convert in the input handler (above). The schema does NOT need to change. If a stricter pattern is preferred (Zod owns the string regex + transform), use:

```ts
supplierValue: z
  .string({ required_error: 'Valor do fornecedor é obrigatório' })
  .regex(/^\d{1,3}(\.\d{3})*(,\d{2})?$|^\d+(,\d{2})?$/, 'Valor do fornecedor inválido')
  .transform((s) => parseFloat(s.replace(/\./g, '').replace(',', '.')))
  .refine((n) => n >= 0, 'Valor do fornecedor não pode ser negativo'),
```

Pick whichever is simpler for the executor (the input-handler approach is recommended; the schema-side regex is a fallback if `v-model` syncing causes confusion).

**A few subtle decisions:**

- **Page title `<h1>`**: per UI-SPEC, one H1 per landmark region — the page H1 lives in `<main>` (which AppShell wraps `<RouterView>` in). The sidebar wordmark in `<aside>` is a separate H1. Both are valid.
- **`formRef` typing as `InstanceType<typeof ProductForm>`** — TS infers ref union from `defineExpose`. The `isSubmitting?.value` chain is needed because the ref might be null during the initial render before BaseDrawer mounts the form.
- **Native `window.confirm`** for the "discard changes?" guard. UI-SPEC line 401 mentions "native browser confirm" explicitly — keeping it simple.
- **`closeCreate` vs the drawer's `@close`**: the drawer emits `requestClose` when `guard-close` is true (= form dirty) and `close` when not. The wiring above handles both: `@close` for clean exits, `@request-close` for guarded ones (calls `closeCreate` which runs the native confirm).
- **Status badge column placement**: in the table, the badge is always rendered (empty cell when `deletedAt === null`). The detail drawer's red `Excluído em` field is the secondary signal per UX-13.
- **No `_links` consumption in v1** — they're emitted by the backend (for LLM consumers) but the UI hardcodes routes/actions. This is intentional and noted in CONTEXT.md `<deferred>`. The `_links.delete` is read implicitly by the Detail drawer's `v-if="!detailProduct.deletedAt"` guard; we don't need to consume `_links` to know whether delete is allowed (the same info is in `deletedAt`).
